# Лор и игровая механика города: план разделения источников

> **Для агентного исполнения:** работать напрямую в vault в пределах запрошенного этапа. Выбирать skill по задаче: `eldraine-design-architect` для решений об ownership, `eldraine-lorekeeper` для спорной fiction causality, `eldraine-gdd-editor` для принятого текста, `eldraine-vault-maintenance` для переносов и ссылок. Это не обязательная последовательность.

**Цель:** Разделить институциональный лор, стабильную идентичность фракций и игровые интерфейсы так, чтобы каждый факт имел одного владельца и не требовал читать художественную страницу как техническую спецификацию.

**Архитектура:** Лорные страницы фракций владеют людьми, происхождением, властью, бытом и конфликтом. Системные страницы `03_Factions_Societies` владеют доверием, поручениями, квестами и адресацией. Реестры владеют стабильными ID и структурированными интерфейсами. Экономика и Хаб исполняют собственные правила, ссылаясь на фракционные ID, а не копируя лор.

**Технологии:** Obsidian Markdown, YAML frontmatter, native Dataview, root-relative Obsidian links.

## Общие ограничения

- Один игроковый параметр имеет одного авторитетного владельца.
- Лорная метафора не является формулой, состоянием или скрытой наградой.
- Механическая страница не пересказывает историю народа или атмосферу учреждения.
- Реестр хранит стабильные поля и представления, но не становится вторым источником прозы.
- Dataview показывает уже существующие данные и не извлекает канон из свободного текста.
- Страница фракции остаётся канонической сущностью с `faction_id`, названием, ролью и отношениями.
- `promise` может остаться в лорной сущности как общественное обещание; `player_label`, перечни услуг, награды и квестовые глаголы переходят в интерфейсный источник.
- Не переносить игровые разделы до завершения институционального прохода: сначала сохранить смысл, затем удалить дублирование.
- Не менять формулы экономики, репутации или доступа только ради красивого разделения файлов.
- Не возвращать старые фракции `Академия Эфира`, `Литейный Синдикат` или `Теневой Картель` как контейнеры механик.
- Не использовать git; работа выполняется только в локальном vault.

### Задача 3: Создать реестр фракционных интерфейсов

**Навык:** `eldraine-gdd-editor`.

**Файл:**

- Создать: `03_Factions_Societies/_Registries/Registry_Faction_Interfaces.md`.
- Изменить: `03_Factions_Societies/_Registries/Registry_Factions.md`.

**Производит:** Единственную структурированную карту отдельных игровых взаимодействий между `faction_id` и профильными системами.

Каждая запись интерфейса должна содержать:

```text
interface_id
faction_id
interface_status
role
input_family
player_verb
result_family
mechanic_owner_ref
dependency_refs
presentation_ref
minimum_boundary
does_not_own
```

- [ ] Определить допустимые значения полей до переноса записей.
- [ ] Создать одну запись на одно самостоятельное взаимодействие, а не одну запись на Очаг.
- [ ] Допустимые базовые роли: `ADDRESS`, `ISSUER`, `PROVIDER`, `WITNESS`, `PRESENTER`, `CONSUMER`.
- [ ] У каждой активной строки ровно один `mechanic_owner_ref`; `dependency_refs` не являются совладельцами.
- [ ] Один Очаг может иметь любое число строк. Не назначать ему один общий `primary_system`.
- [ ] Создать записи для сетей только тогда, когда у них есть самостоятельный системный интерфейс.
- [ ] Хранить ссылки на системные страницы вместо копии их правил.
- [ ] Использовать `MISSING_OWNER`, если механический владелец не найден; не назначать authority лорной странице для заполнения пустоты.
- [ ] Сделать неизвестный `faction_id`, пустой или отсутствующий `mechanic_owner_ref`, дублирующий `interface_id` и дублирующую пару `faction_id + role + player_verb` видимыми в Dataview-проверке.
- [ ] Оставить `Registry_Factions` обзором сущностей, а не ассортиментом услуг.

### Задача 13: Проверить читаемость двух маршрутов

Провести два независимых чтения.

**Лорный маршрут:**

```text
City_Genesis
  -> Civic_Order / Civic_Ethos
  -> Hearth_Anatomy
  -> конкретная фракционная страница
```

**Игровой маршрут:**

```text
Faction_Address_System
  -> Registry_Faction_Interfaces
  -> Reputation / Pledge / Quest
  -> Economy / Hub / POI
```

- [ ] Лорный маршрут отвечает, кто эти люди, кто главный, как устроена власть и почему институт существует.
- [ ] Игровой маршрут отвечает, что вводит игрок, какое правило применяется и какой результат возвращается.
- [ ] Ни один маршрут не требует читать второй для понимания собственной базовой ответственности.
- [ ] Перекрёстные ссылки позволяют перейти к другому слою, когда это действительно нужно.

## 6. Определение завершения

- [ ] Фракционные страницы больше не являются одновременно лором, магазином, квестовым каталогом и системной спецификацией.
- [ ] `Faction_Address_System` находится в системном блоке, а не в папке Lore.
- [ ] Игровые интерфейсы имеют отдельный структурированный реестр.
- [ ] `Registry_Factions` не копирует интерфейсный ассортимент.
- [ ] Точные правила Ward, Welfare, доверия, бартерных адресов и квестовых наград имеют по одному владельцу.
- [ ] Лор Очагов сохраняет людей, власть, имущество, повседневность, внутренний конфликт и тень.
- [ ] Игроковые страницы используют `faction_id` и явные ссылки, а не художественные выводы.
- [ ] Навигация позволяет отдельно читать мир и отдельно реализовывать механику.
